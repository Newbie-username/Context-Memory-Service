# Context & Memory Service 开发计划

**技术基线** 《Context & Memory Service 技术设计说明书》V1.0（2026-11-23）

**仓库基线** 已初始化 Git 仓库，当前只有 README

**状态** 待评审

首期用 IT 知识库问答跑通从业务身份、知识检索到模型输入的完整链路。业务应用通过 Context Service 获取模型消息和上下文清单，再用现有模型服务生成回答。M1 用同一批问题对照现有 RAG，验证授权、回答质量和证据充分性。通过后依次上线受控记忆、任务恢复和企业内网试点。

## 里程碑与投入

排期按两名全职后端工程师估算，QA、SRE、安全和业务接口人按阶段参与。首期 M0–M1 预计 **3–4 周**，M0–M4 预计 **9–12 周**。排期以身份系统、知识库和内网推理测试环境在 M0 可联调为前提，实际工期在 M0 评审时校准。

| 里程碑 | 工期 | 主责 | 交付和阶段出口 |
| --- | --- | --- | --- |
| M0 基线与契约 | 1 周 | 后端、知识库负责人、QA | 冻结首期接口和数据模型，复跑现有 RAG 基线，验证身份、检索权限和 Token 计数 |
| M1 Context Builder MVP | 2–3 周 | 后端、QA | 测试环境中用真实知识库完成端到端构建，必测授权用例全部通过，问答质量和证据充分率达到基线 |
| M2 受控长期记忆 | 2–3 周 | 后端、业务审核负责人 | 已验证记忆可跨会话召回，候选隔离、证据追溯、撤销和后台补偿通过集成测试 |
| M3 压缩与任务恢复 | 2–3 周 | 后端、QA | 多轮任务可跨会话恢复，快照校验、事件重放、并发保护和故障降级通过测试 |
| M4 内网集成与试点 | 2 周 | SRE、QA、安全和业务负责人 | 完成知识库灰度、工单和终端只读联调、压测和回退演练，通过试点准入评审 |

关键路径从 M0 的身份委托与 RAG 证据契约开始，经 M1 的真实知识库回放，进入 M2 和 M3。两名后端可分别承担授权与领域逻辑、适配器与运行集成。QA 从 M0 开始准备对照样本和权限用例。

## 工程选型与模块边界

| 范围 | 计划 |
| --- | --- |
| 应用 | Python、FastAPI、Pydantic，模块化单体。`app/api` 负责 HTTP 契约，`app/core` 承载授权、规则、上下文、记忆和会话逻辑，`app/adapters` 封装内部依赖 |
| 数据与迁移 | PostgreSQL 作为规则、记忆、会话和审计的权威存储。拟用 SQLAlchemy 和 Alembic 管理数据访问和迁移。核心业务表以 `tenant_id` 参与约束和查询，数据库行级安全（RLS）作为第二道租户隔离。迁移账号与应用账号分离，应用在每个事务内绑定租户 |
| 检索与任务 | M1 的问答链路依赖 PostgreSQL 和知识库适配器。M2 启用 pgvector 和 Redis，异步执行拟用 Dramatiq，以事务发件箱记录待处理事件，Redis 充当任务传输通道 |
| 推理与业务权限 | Context Service 提供模型无关的上下文结构。业务应用负责最终生成，M2、M3 的候选提取和压缩通过内网模型适配器执行。业务工具执行层独立校验实时权限、执行操作并生成回执 |

## M0 基线与契约

| 工作项 | 实施与完成标准 |
| --- | --- |
| M0-1 身份与作用域 | 和身份平台确认应用代表用户的委托方式、令牌签发方与受众、角色和资源范围。冻结主体和资源权限矩阵，覆盖跨租户、跨用户、团队、项目、设备及任务访问。用同一资源验证获授权请求和越权请求的处理结果 |
| M0-2 知识库接入 | 拿到现有 RAG 的测试地址、鉴权方式、超时约定和响应样例。用一个真实问题验证检索前的作用域过滤，以及结果中的来源 ID、版本和引用定位。联调样例覆盖授权命中、无匹配证据、权限不足和超时 |
| M0-3 模型与评测基线 | 固定首个内网模型、消息格式、实际窗口、输出预留和 tokenizer。用中文、错误码、工具定义和长文本样例核对计数。建议先准备 30–50 个脱敏知识库问题，标注预期结论、必需证据和可访问主体，预先划分调参和验收样本。记录现有 RAG 的回答正确率、证据充分率、动态输入 Token 和耗时 |
| M0-4 接口与数据评审 | 交付模块边界、OpenAPI 草案、首批表及迁移顺序、规则冲突约定、数据留存分类、测试矩阵和决策记录。明确哪些来源对各任务类型是必需的，并给每项内网依赖指定联调负责人和预计就绪时间 |

M0 结束时，身份和知识库负责人共同确认首期可接入的应用与数据域。依赖延期时可先用固定样例推进契约测试，真实权限和证据回放列为 M1 出口必测项。

## M1 Context Builder MVP

首期构建支持 `knowledge_qa` 和 `general_chat`。知识问答按需检索知识库，普通对话按规则使用会话上下文。M1 定义 `MemoryProvider` 和记忆管理接口契约。构建请求若选用尚未启用的记忆来源，响应标记相应的能力状态。正式记忆从 M2 开始接入。

| 工作项 | 实施与交付 | 依赖 |
| --- | --- | --- |
| M1-1 工程与存储 | 建立应用骨架、`AGENTS.md`、本地运行配置、CI、PostgreSQL 迁移和测试环境。首批迁移覆盖 `tenants`、`policy_versions`、`sessions`、`session_events`、`context_builds`、`audit_events` | M0-4 |
| M1-2 身份、规则与路由 | 校验调用应用与用户身份，解析授权范围。装配已生效的版本化规则，企业强制规则优先，低层规则只能收窄权限。规则冲突或授权信息缺失时按默认拒绝处理。用确定性规则选择任务类型和数据源 | M0-1、M1-1 |
| M1-3 会话与事件 | 创建会话，验证归属后追加事件并分配会话内递增序号。序号分配、事件及关键审计记录与幂等处理在同一事务内完成。首期保存业务提供的必要消息、任务关联和引用，为 M3 的快照和重放建立稳定游标 | M1-1、M1-2 |
| M1-4 知识库适配器 | 对同一个适配器契约提供可重复的测试实现和真实 RAG 实现。按调用主体的授权范围检索并校验返回结果，将来源、版本、时效和信任级别映射为统一 `ContextItem` | M0-2、M1-2 |
| M1-5 构建与清单 | 过滤过期和重复片段，选择同一来源的有效版本。跨来源冲突带出处记录，必需事实无法核实时按证据不足处理。按预算生成模型消息和 Token 用量，对可见片段记录纳入或排除原因，响应前持久化 Context Manifest | M0-3、M1-3、M1-4 |
| M1-6 联调与质量回放 | 接通知识库测试应用，跑单元、数据库集成和端到端测试。用 OpenTelemetry 和 Prometheus 记录请求追踪、依赖耗时、预算和降级。交付运行说明、接口清单、测试结果、基线对比和 V1.0 差异记录 | M1-5 |

M1 回归用例覆盖零预算和负预算、规则冲突、非法作用域、连接池复用下的租户隔离、重复提交会话事件，以及必需来源和可选来源分别超时的响应。真实 RAG 链路还需通过授权命中和拒绝两个端到端用例。

### 首期接口契约

所有业务接口统一使用 `/api/v1` 前缀。租户、最终用户和角色由经校验的委托身份解析，`application_id` 与调用方绑定。模型窗口、输出预留上限和数据源许可由应用配置确定，请求选项可收窄范围。业务写接口使用 `Idempotency-Key` 或版本前置条件。幂等键绑定租户、应用、主体和接口，重复提交时校验授权和请求摘要。同键不同请求返回冲突。

| 接口 | 完成标准 |
| --- | --- |
| `POST /context/build` | 返回 `context_id`、模型消息、警告和预算用量。可选依赖失败时返回明确的降级状态。必需证据缺失或超时时返回 `EVIDENCE_UNAVAILABLE` 或 `DEPENDENCY_TIMEOUT`，固定内容超预算时返回 `CONTEXT_BUDGET_EXCEEDED` |
| `GET /context/{id}/manifest` | 单独校验资源访问和审计权限，返回该次构建的规则版本、证据引用、选取原因、冲突、预算和构建版本。跨权限的排除结果仅记录计数或原因码 |
| `POST /sessions` 和 `POST /sessions/{id}/events` | 创建归属明确的会话，对授权会话追加去重后的事件，返回稳定的事件序号 |
| `GET /health/ready` | 检查主数据库、迁移版本和有效规则配置，供部署探针使用 |

认证失败使用 HTTP 401，作用域拒绝使用 HTTP 403 和 `AUTH_SCOPE_DENIED`，并对越权资源采用统一响应。所有错误返回稳定错误码、`request_id` 和可公开的结构化详情。会话、知识和记忆数据始终以标注来源的非可信数据块交给模型。系统级消息只承载授权配置中的指令。

### Token 分配和溯源

按目标模型的序列化格式计算固定占用 `H`，包含系统消息、当前问题、固定工具定义和必须保留的约束。动态预算用 `B = min(W - O - H - S, ApplicationContextCap)` 计算。`W` 为有效窗口，`O` 为输出预留，`S` 为误差缓冲。`B < 0` 时拒绝构建。初始类别配额沿用设计稿的任务状态 20%、记忆 20%、知识证据 45%、近期会话及必要工具结果 15%。未启用来源和剩余额度按应用配置转给其他类别。

构建完成前对实际模型消息再计数。关键证据无法在预算内完整表示时，返回证据不足并给出机读原因。Manifest 记录已选来源的 ID 和版本、规则版本、模型配置、估算用量和排除原因。日志和指标只记录必要的追踪信息，完整问题及敏感数据按企业留存策略管理。

## M2 受控长期记忆

1. 增加 `memory_entries`、`memory_versions`、`memory_evidence`、`memory_embeddings` 和事务发件箱。用业务方提供的脱敏工单样本和用户确认的个人偏好试跑。工单经验由业务审核人批准，低风险个人偏好按确认规则进入 `verified`。
2. 实现 `candidate → pending_review → verified` 及替代、过期、撤销流程。候选落库前检查秘密和敏感内容，并按来源事件去重。正式版本有证据、有效期、生成模型版本和审批审计。建议补充 `rejected` 终态和原因码。冲突候选进审核队列，审核时遇到过期版本返回 `MEMORY_VERSION_CONFLICT`。
3. 实现 `/memories/search`、`/memories/candidates`、`/memories/{id}/verify`、`/memories/{id}/revoke` 和 `/memories/{id}/versions`。检索先筛授权作用域和有效版本，再按关键词与向量召回。用脱敏中文问题和精确错误码评测召回效果，将 Embedding 模型版本与向量维度一并记录。
4. 在同一事务提交版本变更、审计和待处理事件。后台按事件 ID 幂等更新向量和缓存。返回前回查 PostgreSQL 的可见状态、权限和版本，保证撤销确认后发起的构建即使遇到索引积压也只使用当前有效数据。集成测试覆盖重复投递、并发审批、索引失败和撤销后重建。

## M3 压缩与任务恢复

1. 增加任务状态、任务与会话的关联及 `task_snapshots`。建议每个任务绑定一条权威事件流，授权关联的新会话沿用该流。快照记录任务版本、事件流 ID 和已覆盖序号，迁移保留 M1 的事件和游标。
2. 先清理可重取的重复工具结果，再在占用达到可用输入预算的约 70%–75% 时触发压缩评估。对关键错误、一次性结果、安全证据和未确认的操作结果保留必要内容。模型生成结构化快照，分别保存确认事实、假设、已执行操作、结果、待办和证据引用。
3. 校验 Schema、事实和编号、约束、待办、工具结果以及证据引用。按任务版本和序号提交通过校验的快照，防止晚到的 Worker 覆盖更新的快照。压缩失败时返回 `SNAPSHOT_VALIDATION_FAILED` 或相应的依赖错误，恢复仍可使用最近有效快照和后续事件。首次压缩失败时从授权原始事件重建，超出预算时明确报告。
4. 交付 `/sessions/{id}/compact` 和 `/sessions/{id}/restore`，启用 `task_resume` 路由。恢复按当前权限读取合法快照，补齐到确定的事件序号，核验当前规则和实时数据，返回新的 Manifest。并发状态更新使用版本前置条件，冲突返回 `SESSION_VERSION_CONFLICT`。遇到执行状态不明确的外部动作，通过独立执行层核对操作 ID 和回执后再决定下一步。

## M4 内网集成与试点

- 先灰度 IT 知识库，再接入授权工单和终端遥测只读接口。启用 `ticket_triage`、`incident_diagnosis` 和 `procedure_execution` 对应的上下文策略。人工复核工单分流建议、诊断证据和流程约束，对证据过期、缺失和超时验证降级。接入应用与数据域通过部署配置管理。
- 通过内网镜像仓库和模型端点部署。联调服务间身份、传输与存储加密、最小数据库权限和网络出口限制。演练记忆撤销、删除、备份恢复及恢复后重应用删除记录，核对正式数据、缓存和索引，按企业留存规则处理历史备份。
- 按业务应用配置灰度和回切。异常时关闭对应能力或回切到既有 RAG 链路，回切目标遵循同一数据权限约束。迁移先做向后兼容变更，演练应用回切及异常数据修复。交付环境配置、告警与运行手册、故障演练记录和试点评测报告。

## 验收口径

应在 M0 固定样本、标注规则、模型、生成参数和知识库版本，用同一主体与问题逐条比较现有 RAG 和 Context Service 链路。QA 记录每个样本的回答、所引用证据及用量，业务专家复核有分歧的样本。M1 使用知识库验收集，M2 至 M4 增补记忆、恢复和真实依赖故障场景。

| 指标 | 计算或验证方式 | 阶段门槛 |
| --- | --- | --- |
| 回答正确率和证据充分率 | 分别统计结论正确的比例，以及必需事实均有有效且授权来源支持的比例 | M1 和 M4 均达到同批样本的 RAG 基线 |
| 授权隔离与低信任输入 | 覆盖跨租户和同租户越权、恶意检索文本、RLS、会话和 Manifest 读取、日志泄露 | 各阶段必测越界用例全部通过，越权数据进入响应或模型上下文的次数为零 |
| 撤销及并发一致性 | 在索引滞后、缓存存在、Worker 重试的条件下，撤销确认后从搜索和构建两条路径验证 | M2 起已撤销记忆召回为零，重复请求和并发更新产出唯一有效结果 |
| 压缩保留率 | 在标注样本中逐项核对必须保留的事实、约束和必要证据 | M3 达到 100% |
| 任务恢复正确率 | 核对恢复后的任务状态、事件增量、有效证据和下一步，纳入中断、并发和权限变化用例 | M3 达到至少 95% |
| 动态 Token 节省 | 对比同批样本实际纳入的动态输入 Token 总和，按 `1 - 新链路总量 / 基线总量` 计算，同时检查质量指标 | M1 记录变化，M4 以节省至少 20% 为优化目标 |
| 构建延迟 | 在依赖正常时从 API 接收请求到持久化 Manifest 并响应计时，覆盖检索与内部计算。按约 100 个活跃会话和实测调用间隔制定负载，同时记录吞吐、错误率及降级率 | M4 目标 P95 ≤ 2 秒，最终模型生成单独计时 |

容量验证分别记录活跃会话、请求频率、下游调用次数和存储增长。以 1000–5000 台终端作为目标资产规模，用实测会话行为换算服务负载。试点稳定后再根据运行数据制定 99.9% 可用性的落地安排。

## 关键风险与处理

| 风险 | 处理 | 主责 |
| --- | --- | --- |
| 身份平台无法传递最终用户范围，或 RAG 无法按主体过滤 | M0 用真实委托令牌和越权探针确认。真实联调先限定在明确授权的数据域，权限隔离通过后扩大范围 | 身份和知识库负责人 |
| 中文 Token 计数或消息格式与模型端不一致 | 首期固定一个已校准的模型配置，保留安全缓冲，按适配器实际序列化结果校验输入 | 模型平台、后端 |
| 压缩把推断写成事实，或工具动作处于未知状态 | 校验结构和证据，保留上一有效快照。恢复后以业务执行回执确认动作结果 | 后端、QA、业务系统负责人 |
| 环境或脱敏样本延期 | 按接口契约继续本地测试，真依赖联调和真实样本对照安排在 M1 出口评审，排期随依赖就绪时间调整 | 技术负责人、业务负责人 |

## 首期计划对 V1.0 的细化

- M1 提前实现最小会话事件写入，为上下文历史读取和 M3 重放复用同一序号。完整任务状态机、快照和跨会话恢复在 M3 交付。
- pgvector、Redis 和异步 Worker 随 M2 的记忆链路启用。M1 优先验证 PostgreSQL、身份和现有知识库的真实链路。
- 建议在 M0 评审确认拒绝终态、任务跨会话的权威事件流，以及现有企业任务框架能否沿用。多 Agent 隔离和跨 Agent 记忆共享在单 Agent 试点通过后排期。
